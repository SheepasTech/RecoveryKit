DEBUG LOGGING
=============

Logging is always on. It cannot be switched off.

Where the logs are
------------------
Every run gets its own folder on the kit (the USB):

  cases\<case-id>\<YYYYMMDD-HHMM>\

Before the target disk is known (no case id yet) the run writes to:

  cases\_pending\<YYYYMMDD-HHMM>\

Files in the run folder
-----------------------
  debug.log      everything that happened, one line each, prefixed by type:
                   SCREEN|  every line shown on the screen
                   PROMPT|  every question asked
                   ANSWER|  every answer typed
                   CMD   |  every command, with its exit code and its output
                 plus section starts and ends, file copies, and exceptions with traceback
  audit.log      one JSON object per line for every command attempted, including commands
                 that were refused, declined or only dry-run. Fields: seq, time, kind,
                 purpose, command, argv, exit_code, seconds, timed_out, error, note,
                 output_file
                 A repair writes two lines: first one with kind and note "started" (before it
                 runs, so an interrupted repair leaves a trace), then the result line with the
                 same seq.
  audit\NNNN-<tool>.txt   the full output of each command (NNNN = seq from audit.log)
  inventory\log-findings.json   findings read out of the collected logs (Startup Repair root
                 cause, CBS/DISM errors, setup and device-install failures, notable events, BCD
                 problems), each with the file it came from
  case.json      machine-readable summary of the case
  report.md      human-readable case file

Copy on a normal Windows
------------------------
On a normal Windows a mirror of debug.log also goes to

  %TEMP%\Debug\RecoveryKit\<stamp>\debug.log

like the other ITwork tools. In WinRE %TEMP% is a RAM disk and disappears at reboot, so the copy
on the USB (cases\...) is the one that survives.

Server log
----------
The control server (run.cmd --server) writes its own log to

  <store>\_server-logs\server-<stamp>.log

where <store> is the --store folder (default cases\_server). Relayed jobs are also logged in the
agent's debug.log and audit.log with the operator name.

Secrets
-------
BitLocker recovery keys and other secrets are never logged. They are shown as <hidden> on screen
and <redacted> in the logs. This also holds for the repair record in case.json.

The API bearer token (--serve) and the pairing code (--connect) are deliberately NOT logged: they
are printed on the console only, and the start line (START |, written to debug.log once the case log exists, and also to the copy in %TEMP% where there is one) shows --token and --pin masked.
(--serve also writes its token to cases\_api-token.txt for local programs; the file is deleted
when it exits.)

A scan that stops because the case output would land on the target volume writes debug.log, a partial case.json and
the inventory files of the disks, but no report.md; the reason is in debug.log.

Reporting a problem
-------------------
Keep the whole run folder, above all debug.log and audit.log (and audit\), or run run.cmd --bundle
and keep the zip it writes next to the run folder. Send it with a note of what you expected and what
you saw. The run folder may contain customer data: see docs\manual.md.
